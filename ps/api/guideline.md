# د ادغام لارښود

دا هغه چارې دي چې یو ادغام په اوږده مهال کې سم، ارزان او خوندي ساتي. دا سپارښتنې دي، API هغې نه
پلي کوي، خو ډېرې د ملاتړ پوښتنې د همدې څخه د یوهې پر شاته تګ سره تړاو لري.

## پېژندنه او خوندیتوب

| چاره | ولې |
| --- | --- |
| د هر مصرفوونکي سیسټم لپاره یوه اعتبارنامه | کارونه څرګندېږي او بېرته اخیستل دقیق پاتې کېږي |
| لږې وړتیاوې | د راپور دندې ته `stock:read` یا `orders:read` اړتیا نلري |
| لږې څانګې | یوه سیمه‌ییزه وسیله باید ټولې څانګې ونه لولي |
| پټ کوډ د پټو کلیدونو په مدیر کې | د لاګونو او ذخیرګاهو له لارې افشا کېدل مخنیوي |
| د کارکوونکي له بدلون وروسته څرخول | اعتبارنامه د کارکوونکي واک په میراث بولي |
| هېر شوې اعتبارنامې بېرته اخیستل | چوپ‌تړی ټوکن یوه نه څارل شوې دروازه ده |

بېرر ټوکن هېڅکله په لاګ کې مه ولیکئ. هېڅکله یې په براوزر، موبایل اپلیکېشن یا عامه ذخیرګاه کې مه
ږدئ.

## د ډاټا مدیریت

| چاره | ولې |
| --- | --- |
| د سرچینې `id` د بهرني کیلې په توګه وساتئ | پېژندونکي باثباته دي؛ د بل نمبر کیدای شي سم شي |
| د واټرمارک لپاره `created_at` وساتئ | تدریجي همغږي پرته له تکرارونو ممکنوي |
| مبالغې د اعشاري عددونو په توګه وګورئ | مقدارونه او مبالغې کیدای شي کسري وي |
| د بل اسعارو کوډ وساتئ | API هیڅ د تبادلې محاسبه نه کوي |
| `language_code` ثابت (pin) کړئ | نور نومونه د کاروونکي د انټرفېس ژبه سره بدلیږي |
| له لیبلونو څخه حالت مه حدس کړئ | منطق لپاره `status_id` او ښکارېدو لپاره `status` وکاروئ |

شخصي ډاټا (د پیرودونکو نومونه، ټیلیفونونه، ایمېلونه) د پلور او پېرود په تفصیلونو کې ښکاري. د هغې سره
سمت د خپل شرکت د محرمیت پالیسۍ او د پلیټ‌فارم د شرایطو سره سم چلند وکړئ.

## همغږي (Synchronisation)

1. د هرې سرچینې لپاره جلا واټرمارک وټاکئ، نه یو عمومي.
2. تر ټولو کوچنۍ پاڼه وغواړئ چې د غوښتنو شمېر معقول وساتي؛ د ټاکلي مهال ویش دندو لپاره `per_page=100`
   معمولاً سم دی.
3. پروسس یې idempotent کړئ، یعنی د سرچینې `id` پر بنسټ upsert کول.
4. ودروئ کله چې نوې کرښه دمخه پیژندلې وي.
5. د هرې سرچینې لپاره د ناکامۍ cursor وساتئ، ترڅو یو خراب ریکارډ ټول بند نه کړي.

د هغو ترتیبونو فرضې مه کوئ چې API یې اسناد نه وي کړي. محصولات او ذخیره په `id` ترتیبېږي؛ د سوداګرۍ
سندونه له نوې څخه زوړ وي.

## د تېروتنو سره چلند

| حالت | سم ځواب |
| --- | --- |
| `401` | خبرتیا ورکړئ، اعتبارنامه وڅرخوئ، په تکراري کړۍ کې بیا هڅه مه کوئ |
| `403 api_ability_denied` | خبرتیا ورکړئ؛ په سرچینه سیسټم کې رول بدل شوی دی |
| `403 branch_scope_denied` | ترتیب سم کړئ؛ نورې د څانګې پېژندونکي مه ازموئ |
| `422 branch_required` | `X-Business-Branch` په ډاګانه ډول ولېږئ |
| `429` | `Retry-After` ومنئ، بیا د زیاتېدونکي انتظار (backoff) سره |
| `500` | د زیاتېدونکي انتظار او حد سره بیا هڅه وکړئ؛ د تکراري ناکامیو وروسته خبرتیا ورکړئ |

حالت، `error.code` او ننوتنه لاګ کړئ. هغه د غوښتنې بدانونه چې شخصي ډاټا لري مه لاګ کړئ.

## فعالیت (Performance)

- د چاپېریال ځواب د یوهې دندې د مودې لپاره کاش کړئ، د هر ریکارډ لپاره یې بیا و مه غواړئ.
- د محصولاتو کټالوګ کاش کړئ؛ هغه د پلورونو په پرتله ډېر کم بدلېږي.
- د 100 یوه پاڼه د 25 څلورو پاڼو ته غوره ده.
- درانه همغږي د سوداګرۍ د څوکو ساعاتو بهر ترسره کړئ ترڅو د تعاملي ترافیک څخه لرې وي.
- د HTTP اړیکې بیا وکاروئ او که ستاسو پیرودونکی یې ملاتړ کوي، کمپریشن فعال کړئ.

## نسخه‌بندي او د بدلون مدیریت

- د `/api/v2` پر بنسټ جوړ کړئ؛ v1 یوه دننه سطحه ده.
- د اضافي فیلډونو تحمل وکړئ: په ځوابونو کې کیدای شي نوې کیلي راښکاره شي.
- د JSON په څیزونو کې د فیلډونو ترتیب ته مه تکیه کوئ.
- [د بدلونونو یادښت](/docs/api/changelog) تعقیب کړئ او له بدلونونو وروسته بیا ازموینه وکړئ.
- د ادغام تمې په اتوماتیکو قرارداد ازموینو کې ثابتې کړئ.

## د بیا کتنې چک‌لیست

- [ ] اعتبارنامه د مصرفوونکي سیسټم په نوم نومول شوې ده.
- [ ] یوازې اړینې وړتیاوې ورکړل شوې دي.
- [ ] د څانګې ساحه د سوداګرۍ اړتیا سره سمون لري.
- [ ] پټ کوډ د ذخیرګاهې څخه بهر ساتل شوی دی.
- [ ] واټرمارک د هرې سرچینې لپاره جلا ساتل شوی دی.
- [ ] `429` د `Retry-After` سره مدیریت شوی دی.
- [ ] ټوکن هېڅکله نه دی لاګ شوی.
- [ ] د څرخولو مسؤل او نېټه لیکل شوې ده.
- [ ] ادغام د یوې ازموینیزې (staging) سوداګرۍ پر وړاندې ازمول شوی دی.
