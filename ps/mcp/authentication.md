# د MCP تصدیق

MCP کلاینتونه د HTTP API په څېر د هماغې **سوداګرۍ د ادغام اعتبارنامې** سره تصدیق کېږي. جلا MCP کیلي، د OAuth بهیر یا د هر کلاینت جلا حساب شتون نلري.

اعتبارنامه سوداګري، کارکوونکی، وړتیاوې، څانګې او کوټه ټاکي.

## د MCP لپاره د اعتبارنامې جوړول

1. **ترتیبات > د API ادغامونه** پرانیزئ.
2. د کلاینت په نوم یوه اعتبارنامه جوړه کړئ، د مثال په توګه `Claude Desktop`.
3. هغه وړتیاوې وټاکئ چې مرستیال یې ته اړتیا لري. د عمومي سوداګرۍ پوښتنو لپاره هر پنځه لوستلې وړتیاوې وټاکئ.
4. ټوله سوداګري وټاکئ، یا یې هغې څانګې ته محدوده کړئ چې مرستیال یې باید ویني.
5. پټ کوډ د کلاینت په ترتیب کې کاپي کړئ.

کلاینت چې یوازې د پلور پوښتنو ته ځواب ویلي، یوازې `sales:read` ته اړتیا لري. "د احتیاط لپاره" هر څه ورکول هغه پراخوي چې مرستیال یې افشا کولی شي.

## د کلاینت ترتیبول

| ترتیب | ارزښت |
| --- | --- |
| URL | `https://<app-host>/mcp/business` |
| سرلیک | `Authorization: Bearer <token>` |
| سرلیک | `Accept: application/json, text/event-stream` |
| سرلیک | `Content-Type: application/json` |
| اختیاري سرلیک | `X-Business-Branch: <branch-id>` |

token د کلاینت د پټ کوډ په ساحه یا د چاپیریال متحول (environment variable) کې وساتئ. هېڅکله یې په پرامپټ، چټ پیغام یا شریک شوي ترتیب فایل کې مه اچوئ.

## د وړتیاوو نقشه

| وړتیا | افزار | اړین د پاڼې واک |
| --- | --- | --- |
| `products:read` | `products` | `inventory.products.read` |
| `stock:read` | `stock` | `inventory.branches.read` |
| `purchases:read` | `purchases` | `purchase.purchases.read` |
| `orders:read` | `orders` | `sale.orders.read` |
| `sales:read` | `sales` | `sale.sales.read` |

د افزار بلل هغه وخت ناکامېږي کله چې وړتیا په اعتبارنامه کې نه وي **یا** د کارکوونکي ژوندی رول نور د پاڼې واک ونه لري. دواړه ارزونې اړینې دي، کټ مټ لکه په HTTP API کې.

## ژوندۍ بیا ارزونه

هره MCP غوښتنه لاندې ټکي بیا ارزوي:

1. اعتبارنامه فعاله ده او د token د کاروونکي پورې اړه لري.
2. سوداګري شتون لري او فعاله ده.
3. کاروونکی لا هم په سوداګرۍ کې د کارکوونکي غړیتوب لري.
4. کارکوونکی لا هم د همدې افزار د وړتیا تر شا پروت واک لري.
5. غوښتل شوې څانګه د اعتبارنامې په محدوده کې ده.

که کارکوونکی جابور، لیږدول یا ښکته (demote) شي، راتلونکی د افزار بلل ناکامېږي. د اعتبارنامې له خپلې بل څه لاسي لرې کول پکار نه دي.

## په مکالمو کې د څانګې محدوده

| د اعتبارنامې محدوده | چلند |
| --- | --- |
| د ټولې سوداګرۍ | کولی شي هره فعاله څانګه ولولي؛ د تنګولو لپاره کولی شي `branch_id` ولېږي |
| یوه څانګه ورکړل شوې | څانګه په اتوماتیک ډول ټاکل کېږي؛ `branch_id` اختیاري |
| څو څانګې ورکړل شوې | `branch_id` یا `X-Business-Branch` اړین دی |

ځکه چې مرستیال ممکن داسې څانګې هم پوښتنه وکړي چې تاسو یې په پام کې نه درلوده، سرلیک پر هغې څانګه ونښلوئ چې کلاینت یې باید وکاروي. دا محدوده روښانه کوي او د مکالمې په مینځ کې `422 branch_required` څخه مخنیوی کوي.

## بېرته اخیستل او څرخول

| عمل | په MCP کلاینت اغېز |
| --- | --- |
| څرخول | کلاینت باید له نوي پټ کوډ سره تازه شي؛ زوړ token کار پریږدي |
| بېرته اخیستل | هر د افزار بلل `401` سره ناکامېږي ترڅو نوې اعتبارنامه ترتیب نه وي |
| د وړتیا بدلون | اغېزمن‌شوي افزار ناکامېږي؛ نور خپل کار ته دوام ورکوي |
| د څانګې د محدودې بدلون | له محدودې بهر د افزار بلل `403` سره ناکامېږي |

څرخول د ساتنې (maintenance) په کړکۍ کې پلان کړئ؛ هېڅ داسې مهال نه شته چې دواړه پټ کوډونه پکې کار کوي.

## د خوندیتوب لارښوونې

- د هر AI کلاینت لپاره جلا اعتبارنامه وکاروئ، هېڅکله شریکه نه.
- یوازې د مرستیال د موخې لپاره اړینې وړتیاوې ورکړئ.
- تر ټولو کوچنۍ منطقي د څانګو سیټ ته یې محدوده کړئ.
- token د کلاینت په پټ ځای (secret store) کې وساتئ، نه د پرامپټ په قالب کې.
- `last_used_at` او د غوښتنو پېښې په منظم ډول وکتئ.
- کله چې لیپ‌ټاپ، container یا د کلاینت پروفایل له کاره وغورځول شي، اعتبارنامه بېرته واخلئ.
