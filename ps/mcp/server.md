# د MCP سرور

د سوداګرۍ MCP سرور د **Business Api Server** په نوم ثبت شوی او ځان د یوازې-د-لولستلو د سوداګرۍ د ډاټا افزارونو په توګه تشریح کوي چې د تصدیق‌شوي کارکوونکي پر ژوندۍ سوداګرۍ او د څانګې پر واکونو محدود دي.

دا د **Streamable HTTP** له لارې په یو واحد POST پای ټکي کې وړاندې کېږي.

## پای ټکی

```http
POST /mcp/business
Authorization: Bearer <integration-token>
Content-Type: application/json
Accept: application/json, text/event-stream
X-Business-Branch: 4
```

| خاصیت | ارزښت |
| --- | --- |
| طریقه | یوازې `POST` |
| لاره | `/mcp/business` |
| ترانسپورټ | Streamable HTTP |
| پروتوکول | JSON-RPC 2.0 |
| د ناستې سرلیک | `MCP-Session-Id` |
| تصدیق | د سوداګرۍ له اعتبارنامې څخه Sanctum bearer token |

`GET` او `DELETE` پر دې پای ټکي `405` ستنوي، او د `Allow: POST` سرلیک هم ورسره وي. دا د ترانسپورټ د تړون برخه ده، ستاسو د کلاینت تېروتنه نه ده.

## لاسورکړه (Handshake)

کلاینت د `initialize` غوښتنې سره پیل کوي، بیا افزارونه لیست کوي او ورته بلنه ورکوي:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-06-18",
    "capabilities": {},
    "clientInfo": { "name": "example-client", "version": "1.0.0" }
  }
}
```

ځواب د سرور نوم، نسخه، د پروتوکول نسخه او لارښوونې لري. کلاینت بیا باید `notifications/initialized` ولېږي او کله چې ترانسپورټ یې غواړي، په راتلونکو غوښتنو کې د سرور له خوا ستنېدونکی `MCP-Session-Id` وکاروي.

## د افزارونو کشف

```json
{ "jsonrpc": "2.0", "id": 2, "method": "tools/list", "params": {} }
```

پایله پنځه افزارونه د خپلو JSON سکیمونو او تشریحاتو سره لیست کوي. کلاینت باید خپل د افزار مینو له همدې ځواب څخه جوړ کړي، نه له پخوا سخت‌کوډ شویو نومونو څخه.

## د افزار بلل

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "sales",
    "arguments": {
      "from": "2026-10-01",
      "to": "2026-10-31",
      "per_page": 25,
      "branch_id": 4
    }
  }
}
```

پایله هماغه payload لري لکه د سمون‌لرونکي HTTP پای ټکی، پشمول د لیستونو لپاره `data`، `links` او `meta`. د جزئیاتو بلل `id` مني او سند د توکو او تادیو سره ستنوي.

## د څانګې ټاکل

مخاطبه څانګه په درې ځایونو کې، د لومړیتوب په ترتیب سره ورکول کېږي:

1. د `X-Business-Branch` سرلیک.
2. د `branch_id` د افزار آرګومنت.
3. د غوښتنې پارامترونه.

کله چې یوه مکالمه کېدای شي څو څانګې په پام کې ونیسي، د افزار آرګومنت وکاروئ؛ کله چې ټول کلاینت پر یوه څانګه نښلول شوی وي، سرلیک وکاروئ.

## د سرور برخې

| برخه | شمېر | یادښت |
| --- | --- | --- |
| افزارونه | 5 | توکي، ذخیره، پېرود، ارډرونه، پلور |
| سرچینې | 0 | نه دي وړاندې شوي |
| پرامپټونه | 0 | نه دي وړاندې شوي |

سرور ثابتې سرچینې یا د پرامپټ قالبونه نلري. هر څه د تایید‌شویو آرګومانونو سره د افزار بلل دی.

## محلي سنډبکس

په `local` او `testing` چاپیریالونو کې چې `APP_DEBUG` پکې فعال وي، دوه اضافي پای ټکي ثبتېږي:

| لاره | موخه |
| --- | --- |
| `/mcp/test` | له سوداګرۍ `#1` سره نښلول شوی سنډبکس |
| `/mcp/business/test` | د هماغه سنډبکس مستعار نوم |

سنډبکس اعتبارنامه، کوټه او د audit چارج پریږدي او ازموینې سوداګرۍ ته د ټولې سوداګرۍ د لوستلو واک ورکوي. له محلي/ازموینې بهر `404` ستنوي. هېڅکله یې په production کې مه فعالوئ.

## د inspector سره ډیبګ

```bash
php artisan mcp:inspector
```

inspector تاسو ته اجازه ورکوي چې پر محلي سرور سره بشپړ AI کلاینت له جوړولو پرته افزارونه لیست کړئ، سکیمونه یې وګورئ او وبولي یې.

## عملیاتي یادښتونه

- د MCP پای ټکی د API v2 سره د burst محدودونکی او کوټه شریکوي؛ د افزار هر بلل یوه غوښتنه مصرفوي.
- هر بلل د اعتبارنامې د غوښتنو په پېښو کې د پای ټکي په نوم ثبتېږي.
- سرور جزوي پایلې نه استوري؛ هر افزار یو ځواب ستنوي.
- لویې پایلې باید د `page` او `per_page` له لارې پاژ (page) شي.
- سرور هېڅکله د لیکلو آرګومانونه نه مني، حتی که کلاینت یې ولېږي هم؛ نه‌ملاتړ‌شوي خاصیتونه د تایید پروسې له لارې له پامه غورځول کېږي.
